# 法律经营问数：模型微调与数据实施手册

日期：2026-10-21。配合`01_法律问数项目详细方案.md`使用。

## 1. 交付数据的使用范围

`微调数据/seed_records.jsonl`共60条模拟业务记录，每项能力10条；包含5条“问题→澄清→补充→SQL”的多轮样本。所有记录`synthetic=true`、`review_status=pending_business_and_mysql_review`。这些数据是实际可读、可导入的种子，而非已经审核的正式训练集。

三个训练格式文件：train.json 46条、validation.json 6条、test.json 8条。系统消息包含行为约束，用户消息包含问题及全部六表元数据、指标、字典、关联规则、当前时间和授权范围。assistant是序列化JSON字符串。

这里采用全量六表上下文，便于先排查生成能力。它属于已知正确元数据的受控实验，**不代表生产检索已通过测试**。真实训练应加入检索缺失、干扰字段、别名字典未命中和指标缺口的样本，让模型学习澄清而非编造。

## 3. 输出契约

```json
{
  "action": "sql",
  "sql": "SELECT COUNT(*) AS open_cases FROM v_case WHERE status='OPEN'",
  "question": null,
  "reason": "当前在办案件按OPEN状态统计。",
  "metric_ids": ["open_cases"]
}
```

|动作|sql|question|服务端行为|
|---|---|---|---|
|sql|单条SQL字符串|null|进入SQL校验；模型返回不等于准许执行|
|clarify|null|具体可回答的问题|保存澄清状态，等待补充|
|refuse|null|null|展示原因，不执行，不交给修复器尝试绕过|

reason为简短中文依据；metric_ids必须属于当前批准指标，可空。服务端用JSON Schema/Pydantic一类结构校验约束互斥字段；失败最多重试一次格式修复，仍失败就终止。不要用正则“从长段回答提取第一段SELECT”作为生产契约。

多轮样本中，第一条assistant学习正确澄清，第二条学习补充后的SQL。未来扩充追问样本时，包含旧SQL/条件与新问题，但不包含未来标准答案和查询结果。

## 4. 六种能力的人工审核清单

1. **字段映射**：受理/结案/入账/工作发生时间是否选择正确；contracted_fee是否误当净回款；主办是否误当参与。
2. **值标准化**：值是否真实存在于授权字典；同义词是否唯一；未命中是否补查字典；有多个姓名时是否澄清；不能从大类猜案由。
3. **口径计算**：退款扣除、作废排除、分母、NULLIF、去重、空集合及截止点是否符合指标；比率可能大于1时是否误截断。
4. **澄清**：只询问真正缺失条件；问题能用选项或短语回答；补充后继承已确认条件；当前在办不强制要时间。
5. **关联**：关联键存在；一对多金额不放大；LEFT JOIN的过滤放在合适位置；HAVING条件、TopN并列排序和分组粒度符合问题。
6. **安全/方言**：只读MySQL 8；危险请求正确拒绝；未知函数及未授权对象被系统阻断；SQL可执行与业务正确分别审核。

审核状态建议：draft→schema_checked→mysql_checked→business_approved→frozen；拒绝样本需确认拒绝原因而非运行危险SQL。每条记录保留reviewer、reviewed_at、schema_version、metric_version、fixture_version、错误类型及来源授权范围。

## 5. 如何扩充到正式数据

### 5.1 不先堆数量

先选30—50个真实问题，由SQL工程师和业务负责人共同确认；用真实脱敏快照验证结果。每个场景形成问题、必需上下文、标准动作/SQL、预期结果和陷阱说明。问题可以由教师模型扩写，但标准SQL必须回到业务口径与数据库验证。

6000条建议组成：真实匿名问题及人工标准问法约20%，基于已审场景的合成变体约60%，人工构造的澄清/安全/缺信息难例约20%。这是预算分配目标，实际来源占比必须按收集情况记录，不能把合成问法标为真实日志。

场景变化应涉及时间粒度、枚举别名、单位、分组、聚合、零分母、跨期、缺字段等；只加“请问”“帮我看看”不算新业务覆盖。澄清样本和条件完整样本成对，避免模型把所有难题都澄清。首期只用MySQL 8；未来换PostgreSQL时建立独立方言配置、数据集与测试，不混训没有dialect标签的数据。

### 5.2 防泄漏

先冻结场景模板和SQL AST簇，再按场景分4200/600/1200并做表结构及值归一化近重复检查；同一指标公式可作为共同生产元数据，但同一标准SQL模板及其同义问题不能跨集。多轮前缀与完成对话放同一组。

当前脚本仅做字面值归一化、空白归一化及多轮最终SQL一致性聚类，能避免最明显的重复；别名不同但语义等价的SQL仍可能漏检，正式数据需要AST规范化和人工复查。当前小测试不作为最终冻结测试。

不要将gold_sql、gold_action、业务审核结论或reference_results写进模型输入。数据导出前执行信息泄漏扫描。测试出现错误后形成新训练样本，需要重新建设未见测试或明确测试版本已经发生污染。

### 5.3 数据扰动验证

每种关键SQL至少使用三种快照：常规、空/边界、放大陷阱。包括一个案件多笔收款、多个工时、多人参与，确认不会相乘；增加作废与退款记录，验证净额；同时放入2025-01-01零点、2025-12-31末秒及2026-01-01零点，验证年度边界。

标准SQL与待测SQL在同一只读沙箱比较结果。只有当业务规则本身有独立判定时才称为业务正确；两条错误SQL返回相同结果不是正确证明。


脚本只使用Python标准库，会覆盖本包生成的模拟文件；修改后的人工数据请另存版本，不要直接放进这些生成输出。它不连接业务数据库，也不训练模型。

实际结果：60条记录；46次SQL兼容执行；8项手工核算断言；46/6/8划分；5条多轮；归一化SQL跨集重叠0。参考结果使用SQLite注册DATE_FORMAT和DATEDIFF子集实现，**不能据此声称MySQL 8语法、类型、排序规则和性能已经通过**。

MySQL后续验证：创建专用空沙箱schema，用导入账号运行mysql8_demo.sql，再为检查账号授予这些对象的SELECT；逐条执行sql动作并与参考结果核对。生产还需把模拟表换成受控视图、建立索引与权限，并测试未授权对象访问确实失败。危险样本仅送模型与校验器，不交数据库直接执行。

## 7. 微调配置与运行

### 7.1 训练前置检查

使用隔离Linux GPU环境；锁定LLaMA-Factory仓库commit、Transformers、PyTorch、CUDA、bitsandbytes版本及基础模型revision。先检查所用版本存在`qwen3_nothink`模板和QLoRA配置；样例字段通过官方文档核对，但本机未安装该训练环境。

使用基础模型原始tokenizer统计训练/验证输入＋输出token长度分布（P50/P95/最大值），确保assistant答案未被cutoff_len截断。当前上下文含全部六表，4096也可能不够；先裁剪无关元数据，再按GPU资源增加长度，不能静默截掉规则或SQL答案。记录截断率，正式训练目标为0条答案被截断。

每次至少随机检查10条实际渲染后的chat template，确认system位置、role交替、JSON完整、非思考模板一致；不将`<think>`推理文本插入标签。

### 7.2 可复制训练入口

把整个`微调数据`目录复制到GPU机器，例如`/workspace/legal-finetune/data`，使dataset_info.json与三个数据文件在同一目录。将train_qlora.yaml复制到`/workspace/legal-finetune`，按资源和token检查结果修改。以下是尚未运行的示例命令：

```bash
cd /workspace/legal-finetune
llamafactory-cli train train_qlora.yaml
```

配置默认使用本次模拟数据，仅用于框架联调；正式训练必须切换到已审核数据版本。训练和验证使用不同dataset名称，不再设置随机val_size，防止把已分组的数据重新打散。test不出现在训练配置，不用于选epoch。

数据映射和参数依据：[LLaMA-Factory官方数据说明](https://llamafactory.readthedocs.io/en/latest/getting_started/data_preparation.html)、[LoRA参数说明](https://llamafactory.readthedocs.io/en/latest/advanced/arguments.html)。`qwen3_nothink`模板示例可见[官方QLoRA配置](https://github.com/hiyouga/llamafactory/blob/main/examples/train_qlora/qwen3_lora_sft_otfq.yaml)。本项目8B、学习率与rank是建议试验值，不是复制官方样例得到的效果保证。

### 7.3 训练后验证和发布

根据验证集业务正确率与澄清表现选checkpoint，不用loss单独选；冻结测试只在最终候选比较时运行。报告B与C使用同一检索上下文的差值、每类错误、第一次生成/修复后结果、显存、P50/P95耗时与数据版本。

部署采用训练同版基础权重与adapter，不能给8B adapter换用Coder 7B。可合并LoRA后部署，但合并/量化后必须复测；优先先用固定精度服务确认效果再评估量化损失。通过模型服务的chat template参数关闭思考，不能仅在提示词里写“不要思考”就视为完成配置。[Qwen3官方模式说明](https://huggingface.co/Qwen/Qwen3-8B)

服务端保留`MODEL_VARIANT=base|finetuned`一类版本开关，记录模型和adapter标识。切换后保留同一SQL安全层。若不达验收门槛，交付微调报告并沿用通过验收的基础模型＋语义层，不能把没提升的adapter包装为生产改进。
